# Phase 2 pipeline (core): how to use it

Owner: Member 1. Code: `src/phase2/{data,graph,registry,train,cli,common}.py`. Contract: `reports/phase2_plan.md` section 4. Phase 1 code is imported, never edited (`python scripts/phase2_check_phase1_frozen.py` must print OK).

## Data (`src/phase2/data.py`)
- Source: `data/raw/metr-la.h5`, 34,272 steps x 207 sensors, loaded with the Phase 1 loader. Split and origins come from `data/metadata/split_contract.json` through `get_eligible_sample_origins`: **23,967 / 3,416 / 6,844** origins (train / val / test).
- **Valid reading** = finite and > 0. Zeros, NaN, inf and negatives are unavailable (Phase 1 `create_missingness_mask`). Targets are read from the raw array and are never filled; `y_valid` marks usable targets.
- **Input fill** = forward fill, then the sensor's training median for leading gaps (Phase 1 functions).
- **Scaler** = one global mean and std over valid **training** cells only (mean 58.584, std 12.823 source speed units on the real data).
- **Tensor** `(T, N, 7)` float32, about 199 MB, held on the device. A batch is an index gather; nothing is materialised per window.

| channel | content |
|---|---|
| 0 | z-scored filled speed |
| 1 | missing flag (1 = reading unavailable at that step) |
| 2-3 | hour sin / cos (stored clock) |
| 4-5 | day-of-week sin / cos |
| 6 | is_weekend |

Batch dict: `x [B,12,N,7]`, `y [B,4,N]` (source units, 0 where invalid), `y_valid [B,4,N]`, `origin_idx`, `pos`. Horizons are +1/+3/+6/+12 steps (5/15/30/60 min). Shuffling depends only on `(seed, epoch)`, so resumed runs see the same order.

## Graph (`src/phase2/graph.py`)
`load_graph(variant, seed=0, base="bidirectional")` returns a dense float32 `[207,207]`: `given` (directed), `given_T`, `bidirectional`, `identity`, `shuffled`, `random_matched`. `shuffled` relabels sensors by a fixed derangement (same degrees, wrong neighbours); `random_matched` keeps the edge count. `shuffled` and `random_matched` are derived from `base`; use the same base as the main model.

**Direction:** `A[i, j]` is the Gaussian kernel of the road distance *from sensor i to sensor j* (DCRNN `gen_adj_mx.py`). `P = D^-1 A` with `P @ h` makes sensor `i` read the sensors reachable from `i` (the graph's "downstream"); `given_T` reads the other way. Tested on a 3-node example. The kernel was regenerated from `distances_la_2012.csv` and matches `adj_mx.pkl` (max difference 6e-8, same 1,722 edges). Phase 1 did not verify real traffic direction, so this is the graph's convention only.

## Models
Put a file in `src/phase2/models/` with `@register_model("name")`; it is auto-imported. Contract: `forward(x, adj) -> [B,4,N]` z-scored; optional `attention_maps(x, adj)`. Built-in: `last_value` (Phase 1 persistence, parity test) and `dummy_gru` (pipeline tests only, never reported).

## Running (`python -m src.phase2.cli <cmd> --runs configs/phase2/runs_<name>.yaml`)
| cmd | does |
|---|---|
| `smoke` | 2 train steps + a prediction pass per model on a 1% subset; writes nothing |
| `search` | 4 candidates, seed 42, validation only |
| `pick` | lowest mean validation MAE per group -> `<out>/final/<name>.yaml` |
| `final` | all seeds; writes val + test predictions, `seed<S>_meta.json`, `best/<id>_seed<S>.pt`, attention if available |
| `all` | search, pick, final; skips finished work, resumes interrupted work |

Flags: `--only model_id[:seed]` (final stage), `--device auto|cpu|mps|cuda`, `--subset 0.05`, `--out DIR` (else `$PHASE2_OUT`, else `data/processed/phase2`). Subset runs go to `<out>/subset_<frac>`. `--only` needs a finished pick: run `all` once without it. Changing a run file creates new candidate/run folders (config hash in the folder name), so stale results are never reused.

Example: `python -m src.phase2.cli all --runs configs/phase2/runs_example.yaml --subset 0.05 --device cpu --out /tmp/p2test`

Outputs: `predictions/<id>/seed<S>_{val,test}.npz` (`pred [n,4,207]` source units, `origin_ns`, `sensor_ids`), `seed<S>_meta.json`, `search/<name>.csv`, `final/<name>.yaml`, `checkpoints/...` (`last.pt` every epoch, `best.pt`, `epochs.jsonl`, `done.json`). Test predictions exist only after `final`; the trainer never prints a test metric.

**Full-scale runs of the example file** (`runs_example.yaml`, complete data, 3 epochs per model; tiny dummy models, not project results):
- M3 MPS: 128 s end to end (search of 2 candidates, then 4 final runs), about 6-8 s per epoch, 786 MB peak RSS.
- Colab T4: 45 s for the same run. Validation MAEs agree with the MPS run (for example 3.4434, 3.1432), so MPS and CUDA give the same results here.
- Exported `last_value` files (23,967 / 3,416 / 6,844 origins) reproduce Phase 1 persistence for every horizon and both splits: identical valid counts, MAE and RMSE to 4 decimals (test 5 min: n 1,245,052, MAE 2.8138, RMSE 4.6266).

**Crash test** (real process, full data, MPS): training was stopped with `kill -9` after 3 checkpointed epochs; re-running the same command printed `resumed after epoch 3 (1.2 min used)`, trained epochs 4-8, kept a consistent 8-line `epochs.jsonl`, carried the elapsed time over and wrote the predictions. This is what makes "press Run all again after a Colab disconnect" safe.

## Memory notes (8 GB M3)
Feature tensor 199 MB; a batch of 32 is 12 x 207 x 7 floats per sample (negligible). A model with `[B, heads, N, N]` attention at batch 32 and 4 heads is about 22 MB per layer. Keep `eval_batch_size` equal to `batch_size` unless you have checked memory.
